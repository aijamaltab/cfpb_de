# Паспорт источников данных

Проект: мониторинг жалоб клиентов на банки США (CFPB) в хранилище PostgreSQL. Автор: Табылдиева Айжамал, логин `tabyldieva`.
Формат: по вопросам из шаблона ментора. Технические подробности по каждому источнику (контракт колонок, проверки): `docs/sources.md`.

Три группы источников: **внешние API** (2), **CSV-файлы** (3: событие с датой и два справочника), **«база сайта»** (1, для CDC).
Требование ФТТ «не меньше 2 CSV (событие + справочник) и 1 API» выполнено с запасом.

## 1. Жалобы потребителей CFPB (API)

| Вопрос | Ответ |
|---|---|
| Тип | API |
| Откуда и как достать | `GET https://www.consumerfinance.gov/data-research/consumer-complaints/search/api/v1/` с параметрами `date_received_min`, `date_received_max` (один день), `product`, `size`, `sort`, `no_aggs=true`; страницы листаются курсором `search_after` |
| Ключ или доступ | не нужен. Сайт отдаёт 403 клиенту python-requests, поэтому запрос идёт через `curl` (`ingestion/cfpb_http.py`). Таймаут запроса 30 с, 3 повтора |
| Роль данных | события (жалоба с датой получения) |
| Что отдаёт | `complaint_id`, `date_received`, `product`, `sub_product`, `issue`, `company`, `state`, `company_response`, `timely` (ответ в срок), `submitted_via` (всего 15 полей) |
| Как меняется | каждый день появляются новые жалобы; жалобы за прошлые дни добавляются задним числом (CFPB публикует жалобу после отправки компании), иногда снимаются; у старых жалоб меняются поля ответа компании |
| Сколько | банковские продукты (8 штук): в среднем около 780 жалоб в день; за окно 1 окт 2023 — 30 сен 2026 (1096 дней) загружено 855 110 жалобы. Лимит курса на запуск: 100 тыс. строк |
| Что может сломаться | 1) задним числом добавленные жалобы: свежие ~30 дней всегда недосчитаны (это лечит DAG `cfpb_resync`, раз в неделю); 2) смена имён полей или пустой ответ с кодом 200: загрузка падает, в stg ничего не пишется; 3) WAF отвечает 403 «не браузеру» |
| Куда попадёт | `tabyldieva_stg.stg_cfpb_complaints` → `tabyldieva_ods.ods_complaints` |

Дополнение сверх минимума: второй контур того же API (кредитные бюро и коллекторы, DAG `cfpb_bureau_pipeline`, окно 1 июл — 30 сен 2026, 1 909 762 жалобы) загружается в `stg_cfpb_bureau` → `ods_bureau`. В витрины минимума не входит.

## 2. Показатели банков FDIC (API)

| Вопрос | Ответ |
|---|---|
| Тип | API |
| Откуда и как достать | `GET https://api.fdic.gov/banks/financials` с `filters=REPDTE:<конец квартала>`, `fields=CERT,REPDTE,ASSET,DEP,NETINC,ROA,ROE,EQ,NUMEMP`, `limit=5000`, `offset` |
| Ключ или доступ | не нужен. Таймаут 60 с, 3 повтора |
| Роль данных | справочник размера банка по кварталам (используется в метрике «жалоб на 1 млрд USD активов») |
| Что отдаёт | `CERT` (номер банка), `REPDTE` (дата отчёта), `ASSET` (активы), `DEP` (депозиты), `NETINC`, `ROA`, `ROE`, `EQ`, `NUMEMP`; суммы в тысячах USD |
| Как меняется | раз в квартал появляется новый квартал; пересмотр старых отчётов не проверялся, поэтому каждый запуск перезагружает все кварталы целиком |
| Сколько | 14 кварталов (Q1 2023 — Q2 2026), около 4,5 тыс. банков на квартал, около 63,8 тыс. строк |
| Что может сломаться | 1) последний квартал ещё не опубликован (допустим только в конце ряда); 2) число строк не сошлось с `meta.total` — загрузка падает; 3) в квартале меньше 3000 банков — подозрение на обрезанный ответ |
| Куда попадёт | `tabyldieva_stg.stg_fdic_financials` → `tabyldieva_ods.ods_fdic_financials` (DAG `fdic_financials_pipeline`, раз в месяц) |

## 3. Ставка ФРС FRED DFF (CSV, событие с датой)

| Вопрос | Ответ |
|---|---|
| Тип | файл |
| Откуда и как достать | реальная выгрузка ряда DFF (эффективная ставка по федеральным фондам, % годовых) сайта FRED. Файл `data/fred/DFF.csv` скачивается один раз: `curl -sS -m 60 "https://fred.stlouisfed.org/graph/fredgraph.csv?id=DFF&cosd=2023-10-01" -o data/fred/DFF.csv`. DAG читает файл с диска, а не из сети; только если файл не дотягивает до даты запуска (запуск по расписанию за свежий день), задача пробует докачать ряд той же командой. Если докачать не вышло (у воркера Airflow нет прав на запись в папку проекта) или FRED ещё не опубликовал значение, в ods переносится последняя известная ставка с пометкой `is_carried = true` |
| Ключ или доступ | не нужен |
| Роль данных | события (одна строка на календарный день) |
| Что отдаёт | `observation_date` (дата), `DFF` (ставка, % годовых) |
| Как меняется | ряд дневной: строки есть и за выходные (проверено на выгрузке 22.10.2026); старые значения не правятся. Инкремент имитируем: DAG за дату `ds` берёт из файла одну строку этого дня |
| Сколько | одна строка в сутки, 1096 строк за окно проекта, около 20 КБ |
| Что может сломаться | 1) FRED ещё не опубликовал значение за `ds` (задержка 1–3 дня): в ods переносится последняя известная ставка (`is_carried = true`); если ряд отстаёт больше чем на 14 дней или `ds` раньше начала файла, загрузка падает с понятным текстом, лечится повторным `curl` без `coed`; 2) если значения за день нет, FRED ставит `.` вместо числа: в ods это становится NULL; 3) смена заголовка файла: загрузка падает |
| Куда попадёт | `tabyldieva_stg.stg_fred_dff` → `tabyldieva_ods.ods_fred_dff`; ставка попадает в колонку `fed_funds_rate` витрины `dm_complaints_daily` |

## 4. Справочник компаний (CSV)

| Вопрос | Ответ |
|---|---|
| Тип | файл |
| Откуда и как достать | `data/ref/dim_company.csv`. Составлен вручную по данным самого проекта: 60 компаний с наибольшим числом жалоб (83,2% всех жалоб банковского контура). Каждой компании поставлены каноническое имя, тип и признак «может быть в FDIC» |
| Ключ или доступ | не нужен |
| Роль данных | справочник |
| Что отдаёт | `company_cfpb` (название как в жалобах, ключ), `canonical_name`, `company_type` (одно из 18 значений: `big_bank`, `regional_bank`, `fintech_payments`, `credit_bureau`…), `fdic_candidate` (yes/no), `note` |
| Как меняется | не меняется между запусками; правится вручную, если в рейтинге появилась новая компания |
| Сколько | 60 строк |
| Что может сломаться | 1) неизвестное значение `company_type`: загрузка падает; 2) написание названия компании не совпало с написанием в жалобах: компания в витрине получит тип `other`; 3) BOM в начале файла (учтён: читаем в `utf-8-sig`) |
| Куда попадёт | `tabyldieva_stg.stg_dim_company` → `tabyldieva_ods.ods_dim_company`; тип компании попадает в колонку `company_type` витрины `dm_company_month` |

## 5. Привязка компаний к банкам FDIC (CSV)

| Вопрос | Ответ |
|---|---|
| Тип | файл |
| Откуда и как достать | `data/ref/company_bank_map.csv`. Составлен вручную: 24 компании из жалоб → 25 банков FDIC (номера `cert` подобраны по справочнику FDIC; название банка записано в `bank_name`) |
| Ключ или доступ | не нужен |
| Роль данных | справочник (мост между жалобами и размером банка) |
| Что отдаёт | `company_cfpb`, `cert`, `bank_name`, `note` |
| Как меняется | не меняется между запусками; правится вручную |
| Сколько | 25 строк; покрывает около 43% жалоб банковского контура (остальные относятся к финтеху, бюро, сервисерам, кредитным союзам, которых нет в FDIC) |
| Что может сломаться | 1) слияние банков: `cert` исчезает из FDIC (не проверялось); 2) компания из файла отсутствует в `dim_company`: загрузка падает (проверка есть) |
| Куда попадёт | `tabyldieva_stg.stg_company_bank_map` → `tabyldieva_ods.ods_company_bank` → витрина `dm_bank_size_quarter` |

## 6. «База сайта»: обращения клиентов `tabyldieva.complaint_cases` (источник CDC)

| Вопрос | Ответ |
|---|---|
| Тип | база сайта (OLTP) |
| Откуда и как достать | схема `tabyldieva` на том же сервере Postgres 16, таблица `complaint_cases`. Читаем не запросами, а журналом изменений через Debezium → Kafka → sink-коннектор |
| Ключ или доступ | коннектор работает под ролью владельца таблицы `tabyldieva` (отдельная роль `debezium` с `REPLICATION` не понадобилась), пароль только в переменной окружения `CDC_PASSWORD` (вводится при запуске, в файлах его нет); публикация и слот создаются скриптами `cdc/sql/` |
| Роль данных | сущность: текущее состояние обращения клиента |
| Что отдаёт | события изменений: `op` (`c`/`u`/`d`/`r`), `before`, `after`; поля: `complaint_id`, `product`, `company`, `state`, `status`, `timely`, `received_at`, `updated_at` |
| Как меняется | статус обращения меняется в любой момент: `in_progress` → `closed_explanation` / `closed_relief` / `closed_other` |
| Сколько | на старте обращения за последние 30 дней из `ods_complaints` (порядка 20 тысяч строк при ~780 жалобах в день; точное число покажет `select count(*)`), дальше поток изменений |
| Что может сломаться | 1) забытый слот копит журнал на диске, пока место не кончится (скрипты `99a`, `05` в `cdc/sql/`); 2) без `wal_level = logical` поток не читается; 3) при `REPLICA IDENTITY DEFAULT` в событии нет прежних значений (у таблицы стоит `FULL`) |
| Куда попадёт | `tabyldieva_ods.ods_complaint_cases` (создаёт и пишет sink-коннектор), далее модель dbt `dm_open_cases` |

**Честная оговорка:** у публичного API CFPB нет потока изменений. Таблица `complaint_cases` — имитация внутренней системы обработки обращений банка; номера, продукты и компании взяты из реальных жалоб за последние 30 дней, а смену статусов выполняет скрипт `cdc/sql/04_change_scenario.sql`. Механика CDC настоящая, данные об изменениях синтетические.

## Отброшенные источники
- Население США (Census): сайт заблокирован для сервера, данные годовые, а жалобы помесячные. Источник не используется.
- FDIC `/institutions`, открытые данные Центрального банка Узбекистана, рейтинг жалоб Бразилии: пробовались, из проекта убраны.
